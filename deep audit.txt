Time-T Language Audit: Bugs, Performance, and a Roadmap to Outcompete
24 Sept 2026 · @Gih
Executive Summary
Across three tested releases (v0.9.0 → v0.10.0 → v1.1.0), Time-T has shown a consistent pattern: rapid, honest feature growth paired with untouched core-runtime bugs. Every version has shipped exactly the number of passing tests and byte-exact examples its own changelog claims — that discipline is real and rare. But the same two crash bugs (unhandled division/modulo by zero, unhandled deep recursion) have survived four milestones and a jump to "1.0" without a single line of interpreter.py addressing them, and the README's own "not yet implemented" section has started contradicting the README's own "what exists" section one paragraph above it.
The language's actual strength is narrow and real: for tensor/ML training code, its performance is within 2–5x of hand-written NumPy and matches NumPy outright on raw matmul, because it delegates to NumPy/BLAS. Outside tensor-shaped code — plain loops, control flow, recursion — it is currently 100x+ slower than Python and will crash instead of erroring on ordinary arithmetic mistakes. This document catalogs what's broken, what's genuinely good, and what it would take to make Time-T not just usable but competitive against Python+NumPy, PyTorch/JAX, Julia, and Mojo.

Open Bugs and Drawbacks
1. Division and modulo by zero crash with a raw Python traceback (unfixed across all 4 versions)
5 / 0, 5.0 / 0.0, and 5 % 0 all raise an unhandled ZeroDivisionError straight out of timet/interpreter.py's _eval_binop (return left / right / return left % right, no zero check). The user sees a full Python stack trace instead of one of the project's own E0xxx diagnostics. This is the single most damaging finding: it directly contradicts the project's own stated philosophy ("nothing claimed unless backed by a passing test") — there is simply no test for this path, in any of the 474 tests.
2. Deep recursion crashes with a raw RecursionError
A 100,000-deep recursive call overflows Python's own call stack and surfaces an unhandled traceback rather than a Time-T stack-overflow diagnostic or a documented recursion-depth limit.
3. Interpreter and IR executor are 100x+ slower than Python on non-tensor code
A 10M-iteration scalar while loop took 42–51 seconds under the interpreter/IR engines vs. 0.41s in plain Python and 0.009–0.02s in C. This only stops mattering once a loop body is dominated by tensor ops (see Performance section) — any data preprocessing, custom control-flow-heavy logic, or non-vectorized code written in Time-T will be extremely slow.
4. REPL only accepts bare expressions
let x = 40 fails to parse in the REPL even though it's valid at file scope — meaningfully limits interactive exploration, a normal expectation for a language with a repl subcommand.
5. README's roadmap section is now self-contradicting (regression, first seen in v1.1.0)
The "What does NOT exist yet" list still names structs, mobile/ARM64 backends, and attention as unimplemented — all three of which the "What exists today" section (correctly, and one paragraph earlier) says are done. This is the first documentation error in this project that isn't just incomplete or lagging — it's two sections of the same file actively disagreeing.

6. Native build (time-t build) only covers a narrow, unstated-in-detail subset
It transpiles a "strict, byte-verified subset" to C — confirmed working for simple arithmetic/loop programs, but there's no user-facing list of exactly which language/tensor features are excluded from that subset, so failures there will likely surprise users rather than being self-explanatory.

Upgradability Roadmap
Near-term (biggest ROI per engineering hour):
• Replace the tree-walking interpreter with a real bytecode VM (register- or stack-based). This alone would likely close most of the 100x gap against Python for non-tensor code, independent of any JIT work.
• Cache/compile hot loop bodies detected at IR level — even a simple "loop with no external calls → compile to native and re-enter" tier (a lightweight JIT trigger) would let general-purpose code approach the native-build speed without requiring the programmer to invoke build explicitly.
• Extend the -O1 optimizer with loop-invariant code motion and strength reduction — currently it doesn't help data-dependent loops at all (confirmed: -O1 was slower than -O0 on the scalar benchmark, within noise, but not faster).
Mid-term:
• A real GPU backend (CUDA/ROCm via a NumPy-compatible array library, or a custom kernel layer) — this is the single biggest gap versus PyTorch/JAX for anything beyond toy models, and the README already flags it as unbuilt.
• Static shape typing for tensors (shapes are currently runtime-checked only) — would catch a large class of ML bugs at check time instead of at first run.
• A real module/import system — the current "modules" example is closer to file-splitting than a namespaced package system.
• Generics/traits — needed for a reusable layer/optimizer API that isn't hand-duplicated per type.
Long-term, differentiating bets:
• A true tracing or graph-mode JIT (XLA/Triton-style) that can fuse multiple tensor ops into single kernels — this is where JAX/Mojo pull ahead of eager NumPy-backed systems, and where Time-T's typed IR (already inspectable and JSON-serializable) is a genuine head start most young languages don't have.
• Distributed/multi-GPU training primitives.
• A package manager and ONNX import/export, both already named as roadmap items but not yet started.

Time-T's honest position: it is not yet competitive with any of these alternatives as a general-purpose or production ML tool. Its genuine edge is verification discipline and its typed, inspectable IR — an architectural head start that none of Python, Julia, or early Mojo had at an equivalent stage.
What Would Make Time-T More Powerful Than the Alternatives
Copying PyTorch/JAX feature-for-feature just makes Time-T a slower, smaller version of them. The more interesting path is to lean into what a from-scratch language can do that a Python-hosted framework structurally can't:
1. Make the typed, inspectable IR a first-class debugging surface. time-t inspect --ir already exists — extend it into a step-through IR debugger that shows tensor shapes, gradient flow, and the exact fused-kernel plan before execution. PyTorch/JAX users currently debug graphs through print-statements and external profilers; a built-in, native IR inspector for training graphs is a genuine differentiator, not a catch-up feature.
2. Ship compile-time shape checking as the default, not an opt-in. Shape errors are the single most common class of ML bugs and currently only surface at runtime here (same as PyTorch/NumPy). Since the language already has a real typechecker, extending it to track tensor shapes statically (at least for static-shape cases) would be something none of the mainstream frameworks offer out of the box.
3. Make the native-build path the default deployment story, not a side feature. No mainstream ML framework can hand you a single dependency-free native binary for a trained model today (ONNX/TorchScript still need a runtime). Time-T already compiles to C — investing here (widening the "strict subset" to cover full inference graphs, not just simple programs) would make it uniquely good at exactly the mobile/edge deployment problem its own mobile.py/quantization work already gestures at.
4. Turn the 3-engine differential testing into a user-facing guarantee, not just an internal test. Offer time-t verify that runs any user's program through all three engines and certifies bit-identical results — a trust feature no other ML framework markets, and one that plays directly to Time-T's actual strength (verification discipline) rather than to a strength it doesn't have (raw performance).
5. Close the interpreter-speed gap so the language is viable for the glue code around the tensors, not just the tensors themselves — real ML work is disproportionately data loading, augmentation, and control logic, and today all of that runs 100x slower than Python in Time-T. Fixing this (via the bytecode VM in the roadmap above) is what would let Time-T be used end-to-end rather than only for the innermost training loop.
The honest framing: Time-T's most defensible moat is trust and inspectability (verified execution, typed IR, honest scoping), not speed. Doubling down there — rather than chasing PyTorch on GPU throughput, which is a multi-year, multi-team problem — is the more winnable fight.
